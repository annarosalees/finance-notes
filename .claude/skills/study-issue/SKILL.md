# study-issue: 学習issueの進め方

## このスキルが存在する理由

finance-notesはユーザー本人の金融知識の学習記録であり、`notes/*.md` の本文は
ユーザーが自分の言葉で理解を書き出すことそのものが目的である（詳細は
`CLAUDE.md` と `.specify/memory/constitution.md` の Principle VII「本文執筆の
主体」・Principle VI「対話的な進行」を参照。これらが一次情報源であり、
以下はその実行手順）。

過去に「次のissueに進む」という指示に対してClaudeが先回りして本文を書いて
しまったことがあり、その反省から一時「一切代筆しない・1問ずつ厳密に確認する」
方式にしたが、issue #61での実地テストで「学習用途としては厳しすぎる」という
フィードバックを受けた。そこでユーザーが、別のチャットで実際にうまく機能して
いた「一緒に進めて」形式の共同執筆ワークフローを持ち込み、それを標準の進め方
として採用した。

## モードの選び方

- 依頼文に「一緒に進めて」が含まれる場合 → **共同執筆モード**（下記1〜5章）。
  ドラフト作成を含む。
- それ以外の短い着手指示（「issueに進む」等）の場合 → **壁打ちのみモード**。
  質問・不足の指摘・軽い添削はするが、ドラフト（新しい段落や具体例の丸ごと
  執筆）は作らない。ユーザーから明示的に「代わりに書いて」と言われた範囲
  だけ書く。GitHub操作（commit/push/issueクローズ）は毎回説明の上で承認を
  得てから実行する。

以下、共同執筆モードの手順。

================================================================
## 1. Issueに着手するときの最初の一手
================================================================

ユーザーから「〇〇のIssueを今日やります。内容を教えて、一緒に進めて」と
言われたら：

1. そのIssueの本文（「書く中身」の観点リスト、完了条件）が共有されて
   いなければ、`gh issue view <番号> --repo annarosalees/life-control-panel`
   で取得する（URLまたは番号どちらでも受け付ける。画像やコピペで渡された
   場合はそれを使う）。
2. 観点リストを受け取ったら、**全体の要約は簡潔に1〜2行**で済ませ、すぐに
   ①の観点の質問に進む。長い前置きや、全観点をまとめて説明することはしない。
3. これまでのissue（#1, #56, #57, #60, #61など）で確定した用語・方針・
   社外秘の線引きと矛盾しないか、意識しながら進める（3章参照）。

================================================================
## 2. 観点を1つずつ進める基本サイクル
================================================================

観点リストの①から順に、次のサイクルを1観点ずつ繰り返す。**複数の観点を
一度にまとめて質問したり、まとめてドラフトを作ったりしない。**

### サイクル
1. **質問する**：その観点について、ユーザーに実務者としての説明を口頭で
   聞く。すでに前の観点で出てきた情報と関連しそうなら、その関連も一言
   添えてよい。
2. **ドラフトを作る**：ユーザーの説明をもとに、「3年前の、金融を全く知ら
   なかった自分」が読める文章のドラフトを作る（3章の文体ルールに従う）。
3. **気になる点を提示する**：ドラフトを作る過程で、次のような点に気づいたら、
   確定前に必ず提示して確認する。
   - ユーザーの説明に抜け漏れがありそうな項目（候補を複数挙げて、ユーザーに
     選んでもらう。Claude側で勝手に補って確定させない）
   - 用語や説明が、実際の商品・状況に対して不正確・不適切に見える点
   - 社外秘に触れていないか（3-3章参照）
   - すでに確定した他の観点・他のissueの内容と矛盾していないか
4. **回答を反映する**：ユーザーが選択・訂正・追加した内容を反映して、
   ドラフトを更新する。ユーザーが明確に誤りを訂正した場合は、その訂正を
   正として書き直す。
5. **確定し、次に進む**：その観点が確定したら、次の観点に進む。「①は確定
   です。次は②に進みます」のように、区切りを明示する。

### 質問の出し方の型
- 「〇〇について、実務者としてどう説明しますか？」と、ユーザーの言葉を
  引き出す聞き方をする。
- Claude側から先に完成形を出さない。まずユーザーの説明を聞き、それを土台
  にする。
- 選択肢を挙げて選んでもらう場面（抜け漏れの確認、線引きの確認など）では、
  2〜4個程度の具体的な候補を出し、「当てはまるものを選んでください」と聞く。

## 3. 執筆方針（すでに確定済みのルール）
================================================================

### 3-1. 文体・読者像
- 読者像＝「3年前の、金融を全く知らなかった自分」。専門用語は初出でルビ
  （読みがな）を振る（例：限月／げんげつ）。
- である調。区切り線は `---`。
- 抽象的な説明の後には、可能な限り**具体例**（できれば同じ商品、例：WTI
  原油）で対比させる。表（Markdownテーブル）が向く内容は表にする。
- 分量が多くなっても、内容を削って簡素化しない。ユーザーが実務者として
  説明した内容は、無理に短くまとめようとせず書ききる（2026-09-23、
  issue #62での壁打ち中に「補足切り出しルールのせいで簡素化されすぎる」
  という指摘を受けて方針変更）。
- 1つの観点・1つのノートがどんどん長くなっていく場合は、その場で内容を
  削るのではなく、将来的にノートファイル自体を項目ごとに分割すること
  （例：`notes/cfd.md`から特定トピックを独立ノートに切り出す。issue #87
  で実施済み）を検討する。
  分割するかどうか・いつ分割するかはユーザーの判断を待ち、Claude側から
  勝手に分割・省略しない。

### 3-2. 不明点の扱い
- 想像で埋めない。Claude側の一般知識や他のAIの回答を使う場合も、それを
  そのまま確定情報として書かず、**ユーザーに実務者として正しいか確認して
  から**書く。
- 確認が必要だが今は分からない内容は、`<!-- -->` の隠しメモとしてファイル
  内に残し、確認後に追記する（「分かりやすさの調整」目的では使わない。
  あくまで「事実として未確認」な場合に使う）。

### 3-3. 社外秘の線引き
- 書いてよい：一般公開されている参照先取引所名（SGX、CMEなど）、業界一般
  の仕組み・用語。
- 書かない：勤務先固有の内部レート、契約している具体的なカバー先の名前、
  契約しているデータプロバイダーの具体的な社名（一般化して「大手データ
  ベンダー各社」のように書く）、その他システムの詳細。
- 判断に迷う場合は、必ずユーザーに確認する（Claude側で勝手に「これは大丈夫
  だろう」と判断して書かない）。

### 3-4. バイリンガル化
- 構成：拡張子で言語を分離する（`notes/cfd-basics.md`＝日本語、
  `notes/cfd-basics.en.md`＝英語）。フォルダ分割は採用しない。
- 各言語ファイルの先頭に、もう一方の言語への相互リンクを入れる。
- 英語版は、ユーザーが明示的に指示するまで自動で作成しない。日本語版の
  セクションが確定したタイミングで、「英語版も作りますか？」と一度確認する。
- 2026-10-01時点、CFDノートの英語版（`notes/cfd*.en.md`）は、日本語版の
  全セクションが翻訳済み。`notes/fx.en.md` も日本語版に追いついている。
  新しいセクションを追加した際は、英語版が追いついているか都度確認する。

### 3-5. 用語・構造の確定事項
- CFDは金融派生商品（デリバティブ取引）の一種。基本となるデリバティブ取引は
  先物・オプション・スワップの3つ（三大デリバティブ）で、CFD（差金決済取引）
  はそれらとは別のデリバティブ取引として位置づける。差金決済の仕組み自体は
  CFD特有ではない（例：日経225先物のSQによる現金決済）。
- FXはCFDの一種（為替を対象にしたCFD）だが、実務上の扱いが独立している
  ため別冊のノートとして扱う。
- 貸株の説明は「ロング／ショート」の項目（issue #60）で扱う。
- 異常な値動きを検知したときに顧客へのレート配信を一旦止める仕組みは、
  社内の呼び方（「アボート」）を使わず、「異常レートの配信停止（異常レー
  ト判定）」と書く。業者によって「異常レート判定」「レートフィルター」と
  も呼ばれる。（レビュー②）
- レート生成とカバー（ヘッジ）は別の業務・別プロセス。顧客向けレートは
  データベンダーの価格がもと、カバーはカバー先が提示するレートで約定する。
  カバー先の約定拒否は「約定拒否（ラストルックなど）」と書く（ラストルッ
  クは約定拒否の一形態）。カバーディールの項目（issue #62）で扱う。
- リミットの用語：「ポジションリミット」＝これを超えたら自動カバーが発動
  する保有量の上限。「1回あたりのカバー数量の上限」＝大きな量を分割して
  カバーするための1注文あたりの上限。社内の設定名（リミット／リターン／
  カバー目安など）は使わない。（レビュー②。`cfd-product-listing.md` の
  「カバーリミット」はレビュー⑤で揃える）
- 業者側の「顧客に対する売り」と「市場での買い」の組み合わせは「両建て」
  と呼ばない（「両建て」は顧客が同じ銘柄で買いと売りを同時に持つことを
  指す。cfd-basics で定義）。
- 商品タイプの違いは「参照先（先物／個別株・ETF／スポット）」を軸に整理
  する。扱いを決めるのは商品名ではなく参照先（例：同じ貴金属でも、金スポ
  ットはFXと同じしくみ、貴金属先物は通常の乗り換え）。（issue #64）
- 「金利調整額」「権利調整額」は2つの意味で使い分ける。先物では先物価格
  に織り込まれた「中身」（顧客が受け払いするのは価格調整額）、個別株・
  ETF・スポットでは顧客口座で直接受け払いする調整金そのもの。（issue #64）
- 先物を参照する株価指数CFDでは、配当は配当のタイミングで受け払いせず、
  乗り換え時の価格調整額の中で精算される。（issue #64）
- 先物の価格差を決める要素は、株価指数では金利と配当、商品では金利に加え
  て保管コストと需給（コンタンゴ／バックワーデーション）。（issue #64）
- 日本の個人向けCFDのレバレッジ上限は商品タイプ別：株価指数10倍・商品
  20倍・個別株/ETF 5倍・債券50倍（FXは25倍）。（issue #64）
- ETFの配当にあたるものは「分配金」と呼ぶ。
- 調整金は、日次の値洗い（清算処理）のタイミングでまとめて計算・付与す
  るのが一般的。価格調整額は、清算価格を使う業者とMIDを使う業者がある。
  （issue #64）
- CFDノートは、issue #87 でテーマごとに分割した。`notes/cfd.md` は目次
  （入口）で、本文は次の5ファイルにある。新しい項目は、テーマの合う
  ファイルに追加し、`notes/cfd.md` の目次も更新する（英語版も同じ構成）。
  - `notes/cfd-basics.md`：基礎（CFDとは何か〜ロング／ショート）
  - `notes/cfd-pricing-and-cover.md`：価格とリスク管理（レート生成・
    カバーディール・ポジションリミット）
  - `notes/cfd-rollover-and-adjustments.md`：乗り換えと調整金（乗り換え・
    限月・スピンオフ等・配当）
  - `notes/cfd-product-types.md`：商品タイプ別の具体例
  - `notes/cfd-product-listing.md`：銘柄追加の実務（issue #85）
- ファイルをまたぐ参照は、「〇〇」をリンクにする（例：
  `[「配当が出たとき（権利調整額）」](./cfd-rollover-and-adjustments.md)`）。
  同じファイル内の参照は、リンクにしない。
- 英語版では、権利調整額を「rights adjustment」と訳す（配当だけでなく、
  スピンオフなど配当以外の権利の調整にも使うため）。各ファイルの初出に
  「(an adjustment for dividends and other shareholder rights)」と添える。
  （issue #87）
- 価格データを受け取るデータベンダー（配信元）と、カバー取引の相手である
  カバー先は、基本的に別の相手として書き分ける。ノート内の「CP」はカバー
  先を指す。（issue #85）
- 法令で定められた数値（レバレッジ上限など）は、変更される可能性がある
  ため、書く場合は「執筆時点」と添える。銘柄追加の項目（issue #85）では
  数値に触れず、上限があることだけを書く。
- 社内システムの設定画面の項目名・パラメータ名・システム名は書かず、
  「どんな考え方で価格を守っているか」という仕組みを業界一般の言葉で
  書く。（issue #85）

### 3-6. 今後扱う予定のメモ

  - `cfd-product-types.md` の「受け取りになりやすい（配当の影響）」（株価

  違う。内容は変えずに折り返しだけ揃える（表示には影響しない）。

## 4. 全観点が確定したあとの流れ
================================================================

1. 確定した全観点をまとめて振り返り、「抜け漏れはないか」をユーザーに
   一度確認する。
2. ユーザーから明示的な指示（「HANDOFFにして」「反映して」など）が出ない
   限り、`notes/*.md` やissueへの実際の書き込み・pushは行わない。
3. 指示が出たら、次を1つのHANDOFFとしてまとめる：
   - `notes/cfd.md`（等）への実装内容（目次チェックボックスの更新、
     セクションの挿入位置、確定した本文）
   - 英語版を作る場合は `notes/cfd.en.md`（等）への反映内容
   - `life-control-panel` の該当issueのクローズ（またはチェックリスト更新）
4. 実装後、issueのクローズや次のissueへの移行は、ユーザーの指示を待つ。

================================================================
## 5. やってはいけないこと
================================================================

- 観点を複数まとめて一度に処理すること
- ユーザーの説明を待たずに、Claudeの一般知識だけで確定文を作ること
- 社外秘にあたるかどうかを自己判断して書き進めること
- 英語版を確認なしに自動生成すること
- 全観点の確定を待たずに、`notes/*.md` やGitHubへの実装・pushを行うこと
- 「効率化」を理由に、質問や確認のステップを省略すること
